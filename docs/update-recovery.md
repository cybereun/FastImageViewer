# Windows 업데이트와 실행 경로

## 2.0.9 이후의 업데이트 완료 기준

다운로드 완료나 실행 명령 전송만으로 성공 처리하지 않는다. 새 프로세스가 예상 버전·기존 실행 경로·이번 업데이트 토큰을 가지고 시작하고, 창이 표시되며 React 화면이 로드된 뒤 보내는 확인 신호를 받아야 성공이다.

1. 앱이 실행 중일 때 보조 프로그램 시작, SHA-256 재검증, 포터블 교체 파일 사전 복사를 확인한다. 준비에 실패하면 앱을 종료하지 않는다.
2. 업데이트 적용 승인을 보조 프로그램에 전달하고 기존 프로세스의 종료를 기다린다. 종료하지 않는 앱을 강제로 죽여 설치하지 않는다.
3. 포터블은 원래 파일을 백업하고 같은 경로에 교체한다. 설치형은 NSIS 종료 코드 확인 후 기존 설치 경로의 EXE를 직접 실행한다.
4. 실제 화면 확인을 기다린다. 실패하면 실행을 한 번 더 시도한다. 포터블은 두 번 모두 실패하면 원래 EXE 바이트를 복구하고 이전 버전을 실행한다.
5. 성공 확인 후에만 백업과 다운로드 파일을 정리한다. 정리 실패는 성공한 업데이트를 되돌리지 않는다.

종료 후에는 별도 진행창을 표시한다. 앱이 다시 열리면 완료 또는 복구 결과를 안내한다. 실패 시 보조 프로그램은 오류창과 `updates/<업데이트 ID>/helper.log`, `status.json`을 남긴다. 설치 파일이 손상되거나 외부 프로그램이 실행을 차단하는 상황까지 무조건 성공시키는 것은 불가능하므로, 설치형 복구가 불가능한 경우 이를 성공으로 표시하지 않는다.

일반적인 앱 시작 시에는 미완료 업데이트를 자동 재시도하지 않는다. 사용자가 업데이트를 다시 요청해야 하므로 실행할 때마다 종료되는 반복이 발생하지 않는다.

PowerShell은 이전 포터블 실행 변수와 다른 PowerShell 버전의 모듈 경로를 상속하지 않도록 실행한다. 한글·공백·따옴표 경로와 Windows 8.3 경로를 처리하며, 중복 적용 요청은 하나로 묶는다. 설치형 압축은 ZIP 해제 오류를 피하기 위해 7z 방식을 사용한다.

일부 Windows 환경에서 Node의 `detached: true`로 Windows PowerShell을 시작하면 종료 코드는 0이지만 스크립트가 전혀 실행되지 않는 현상을 재현했다. 2.0.9는 분리된 CMD 중계 프로세스가 숨김 PowerShell을 새 콘솔에서 실행하도록 한다. 사용자 경로는 UTF-16 Base64로 전달해 셸 특수문자의 해석을 방지한다. 부모 앱이 종료되어도 보조 프로그램이 계속 실행되는지는 별도의 실제 IPC 통합 시험으로 확인한다. 2.0.8의 배포는 이 문제를 확인하면서 중단했다.

### 배포 검증

- `npm test`: 버전 비교, 방향 처리, 체크섬·설치 형식, 중복 요청, 종료 실패, 재실행 확인, 복구 등의 회귀 테스트
- `node scripts/verify-package.mjs`: ASAR 내부 파일의 무결성과 버전 확인
- `node scripts/update-manager-e2e.mjs`: 이전 버전 번호를 사용하는 시험용 앱에서 실제 업데이트 IPC를 호출하고, 부모 앱 종료 후 새 패키지의 화면 확인
- `node scripts/update-e2e.mjs portable`: 별도 프로필의 실제 포터블 창을 종료하고 파일 교체 및 새 프로세스의 화면 확인
- `node scripts/update-e2e.mjs rollback`: 실행 불가능한 업데이트를 넣고 기존 파일의 해시와 재실행 확인
- `node scripts/build-update-test-installer.mjs` 및 `node scripts/update-e2e.mjs installer <시험용 Setup 경로>`: 별도 appId로 설치·업데이트·재실행 후 시험용 앱 제거

GitHub 릴리스는 위 검증이 통과한 뒤 게시된다. 설치형 시험은 사용자 FastImage 설치 정보, 바로가기, 파일 연결과 분리한다.

포터블 자동 업데이트는 현재 실행 중인 EXE의 경로와 파일명을 유지하고 내용을 새 버전으로 교체한다. 따라서 파일명에 이전 버전이 적혀 있어도 기존 바로가기를 계속 사용할 수 있다. 실제 버전은 앱에서 확인한다. 수동으로 새 EXE를 다른 위치에 저장했다면 바로가기 대상도 새 위치로 변경해야 한다.

설치형은 설치 폴더와 설치 프로그램이 만든 바로가기를 사용한다. 자동 업데이트는 NSIS를 `/S --force-run --updated`로 실행해야 설치 후 앱이 다시 열린다. `runAfterFinish: true`만으로는 현재의 assisted installer에서 무인 업데이트 후 실행이 보장되지 않는다.

## 2026-09-05 확인 및 수정

- 사용자 PC의 2.0.5 바로가기 대상은 존재했지만, EXE는 교체되지 않았고 2.0.6 다운로드와 pending manifest가 남아 있었다. 반복 생성된 PowerShell 스크립트도 남아 있었다. 기존 코드가 오류를 기록하지 않아 당시 보조 프로세스가 실패한 정확한 원인은 확정할 수 없다.
- 다운로드된 2.0.6의 SHA-256을 manifest와 대조하고 기존 EXE를 백업한 후 동일 경로에 복사했다. 대기 manifest를 보관용 이름으로 복사하고 제거한 뒤 실제 앱 창의 실행을 확인했다.
- 업데이트 보조 프로세스는 임시 압축 해제 폴더 대신 업데이트 폴더에서 시작하고, PowerShell 준비 신호를 받은 뒤 앱을 종료한다. 시작 오류나 시간 초과 시 앱을 유지한다.
- 포터블 런처가 EXE를 잠시 더 점유하는 경우 교체를 최대 60초 재시도한다. 교체 실패를 `updates/pending-update.json.log`에 기록한다.
- 적용 시도 이력을 manifest에 남겨 다음 시작에서 자동 적용을 반복하며 앱이 종료되는 현상을 방지한다. 사용자가 업데이트를 다시 요청할 수 있다.
- 설치형 자동 업데이트에 재실행 옵션을 추가했다.

Windows PowerShell에서 파일 잠금 재시도, 기존 경로로 실행 요청, 실패 시 기존 파일 유지 및 오류 기록, NSIS 실행 인수, 보조 프로그램 실패 시 종료/자동 재시도 방지 등 업데이트 관련 테스트 9개를 통과했다. NSIS 테스트는 실행 호출을 대체하므로 실제 설치형 업그레이드 전체 검증은 별도로 필요하다.

이 수정은 2.0.7에 포함된다. 기존에 배포한 2.0.5/2.0.6 바이너리에 소급 적용되지 않으므로, 재발 방지 기능을 사용하려면 2.0.7로 한 번 수동 교체 또는 설치하는 것이 좋다.
